# Transfer API Contract

This document is the authoritative backend contract for the assessment. The in-repository Ktor stub implements it deterministically. Production-like failures can be selected through separate control endpoints; application code must not depend on those control endpoints.

## Create an immediate transfer

```http
POST /v1/transfers
Content-Type: application/json
Idempotency-Key: <operation-id>
```

Example request:

```json
{
  "fromAccountId": "acc-checking-eur",
  "toAccountId": "ben-alex",
  "amountMinorUnits": 12500,
  "currency": "EUR",
  "scheduledFor": null
}
```

`Idempotency-Key` is required and is the stable identifier of the customer intent. It is generated by the client before the first submission and must be retained for recovery or protocol-level resubmission.

For this synthetic fixture, `toAccountId` accepts either the beneficiary identifier returned by `/v1/beneficiaries` (for example, `ben-alex`) or that beneficiary's underlying account identifier. The mobile read model currently uses the beneficiary identifier. This compatibility rule does not authorize arbitrary destination IDs.

Example accepted response:

```json
{
  "transferId": "transfer-42",
  "operationId": "01J00000000000000000000000",
  "fromAccountId": "acc-checking-eur",
  "toAccountId": "ben-alex",
  "amountMinorUnits": 12500,
  "currency": "EUR",
  "reference": null,
  "status": "PROCESSING",
  "createdAt": "2026-08-19T10:15:30Z",
  "updatedAt": "2026-08-19T10:15:30Z"
}
```

The service can return a terminal status immediately, but callers must also support `PROCESSING`.

### Idempotency semantics

- The first valid request claims the operation identifier and stores a payload fingerprint.
- Repeating the same identifier with the same canonical payload returns the original operation. It does not create another transfer.
- Repeating the same identifier with a different canonical payload returns `409 Conflict`.
- The payload fingerprint covers source account, destination account, amount in minor units, currency, and reference.
- The key is opaque to the server. Its format is less important than stability and uniqueness across customer intents.
- Idempotency is a client/server protocol. A UI debounce, local mutex, or connectivity check does not replace it.

### Responses

| Status | Meaning | Client interpretation |
|---:|---|---|
| `200` | Existing operation returned for the same key and payload | Observe/reconcile returned operation |
| `202` | New operation accepted | Persist/observe the returned operation |
| `400` | Invalid payload | Definitive input failure; do not blind-retry |
| `401` | Session not accepted | Re-authenticate according to session policy |
| `409` | Key already represents a different payload | Protocol conflict; never generate a replacement key automatically |
| `422` | Definitive business rejection | Terminal rejection with safe user-facing reason |
| `5xx` | Service error | Outcome may be unknown unless the response contract proves rejection |

Cancellation, timeout, connection loss, malformed response, or app termination can happen after server commit. They are not evidence that the transfer failed.

Error responses use this shape:

```json
{
  "code": "RESPONSE_LOST_AFTER_COMMIT",
  "message": "The response was lost after the transfer was committed",
  "retriable": true,
  "outcome": "UNKNOWN_TO_CLIENT"
}
```

`outcome` is `NOT_APPLICABLE`, `NOT_COMMITTED`, or `UNKNOWN_TO_CLIENT`. A response that is successfully received and explicitly reports `NOT_COMMITTED` can support a different recovery choice from a client timeout, parse failure, or `UNKNOWN_TO_CLIENT`. `retriable` means the server considers another protocol attempt possible; it does not authorize the mobile client to create a new operation identifier or altered payload.

## Read status by operation identifier

```http
GET /v1/transfers/by-operation/{operationId}
```

Example response:

```json
{
  "transferId": "transfer-42",
  "operationId": "01J00000000000000000000000",
  "fromAccountId": "acc-checking-eur",
  "toAccountId": "ben-alex",
  "amountMinorUnits": 12500,
  "currency": "EUR",
  "reference": null,
  "status": "COMPLETED",
  "createdAt": "2026-08-19T10:15:30Z",
  "updatedAt": "2026-08-19T10:16:04Z"
}
```

Possible statuses are:

- `PROCESSING`: accepted, non-terminal;
- `COMPLETED`: terminal success;
- `REJECTED`: terminal business rejection.

`404` means the service has no operation for the identifier at the time of the lookup. Whether another create call is safe depends on the selected recovery protocol, elapsed/retry policy, and idempotency contract. A single `404` must not silently become a new customer intent.

Status is also available by server transfer identifier:

```http
GET /v1/transfers/{transferId}
```

Recovery should prefer the operation identifier because it exists before a create response is available.

## Other application endpoints

```http
GET /v1/accounts
GET /v1/beneficiaries
GET /health
```

Accounts and beneficiaries are read models. Cached account data can be shown when offline if it is visibly marked with its freshness. It is not an authoritative proof of the available balance after an ambiguous transfer outcome.

## Deterministic stub controls

The controls below exist only for local validation and tests:

```http
GET  /__control/faults
PUT  /__control/faults
GET  /__control/journal
POST /__control/release-blocked
POST /__control/reset
```

`PUT /__control/faults` accepts:

```json
{
  "submitMode": "COMMIT_THEN_TIMEOUT",
  "submitModeApplications": 1,
  "submitDelayMillis": 10000,
  "statusFailuresBeforeSuccess": 0,
  "completeAfterSuccessfulStatusChecks": 1,
  "terminalStatus": "COMPLETED"
}
```

Supported `submitMode` values:

- `NORMAL`;
- `REJECT_BEFORE_COMMIT`;
- `COMMIT_THEN_TIMEOUT`;
- `COMMIT_THEN_MALFORMED_RESPONSE`;
- `BLOCK_AFTER_COMMIT`.

`POST /__control/release-blocked` releases requests held after commit. `GET /__control/journal` reports accepted intents and invocation counts so validation can assert externally meaningful behavior. Always reset control state between scenarios. Do not add a production dependency on a control route.

## Compatibility expectations

- Unknown response fields must not break supported clients.
- A client must not infer terminal success from a local write or terminal rejection from a transport error.
- Existing and updated clients can coexist only while they honor the same idempotency-key meaning.
- If a mobile release changes payload canonicalization, coordinate fingerprint compatibility with the backend before rollout.
- Scheduled payments use the same create/status protocol; preserve their occurrence identifier and scheduled payload semantics.
